# VGGT 模块一测试操作手册

版本：0.1（待小组评审）  
适用阶段：软件测试与质量保证实践——模块一  
被测模块：`vggt-main/vggt/utils/geometry.py`  
文档状态：操作框架已建立；计分测试内容与结果待小组成员人工完成

## 1. 手册用途与合规边界

本手册说明如何准备环境、启动 VGGT 可视化、接入并运行小组人工编写的模块一测试、保存证据以及填写课程附录。

课程要求模块一不得使用 AI 工具生成测试用例或开展自动化测试。因此，本仓库当前不提供 AI 生成的计分用例、pytest 测试代码、正式执行结果或缺陷结论。小组成员应独立完成这些内容，并保留个人 Git 提交记录。

## 2. 目录与文件

- `vggt-main/`：被测软件与现有中文 Gradio 可视化程序，默认保持不变。
- `vggt_input/`：图片序列和视频输入素材。
- `vggt_output/`：可视化和指标工具生成的可再生产物。
- `tests/`：小组成员人工编写的模块一测试代码。
- `test_results/module1/`：测试日志、JUnit XML、截图和复测证据。
- `deliverables/module1/`：测试用例清单、缺陷报告、测试报告、操作手册和检查清单。
- `run_vggt_demo.ps1`：从正确工作目录启动现有 `demo_gradio_cn.py`。
- `run_tests.ps1`：预留的一键测试入口，由小组成员人工创建。

## 3. 环境准备

1. 确认 Windows 能正常识别 NVIDIA GPU 和 CUDA。
2. 确认 Conda 环境 `Pytorch_Vggt` 存在，其 Python 默认路径为 `D:\anaconda3\envs\Pytorch_Vggt\python.exe`。
3. 确认模型权重位于 `E:\办公\研一\1软件实践\model.pt`。
4. 确认 `Software_testing/vggt-main/requirements.txt` 和 `requirements_demo.txt` 中的依赖已安装。
5. 模型权重体积较大，不应提交到课程 Git 仓库；应在 README 中记录合法获取方式、存放位置和必要的校验信息。

## 4. 启动和停止可视化

### 4.1 推荐方式

在 `Software_testing` 根目录打开 PowerShell，运行：

```powershell
powershell -ExecutionPolicy Bypass -File .\run_vggt_demo.ps1
```

脚本会检查模型权重和 Python，自动把当前工作目录切换到 `vggt-main`，然后调用原始 `demo_gradio_cn.py`。

如需指定 Python：

```powershell
.\run_vggt_demo.ps1 -PythonExecutable "D:\anaconda3\envs\Pytorch_Vggt\python.exe"
```

### 4.2 直接运行原程序

```powershell
Set-Location "E:\办公\研一\1软件实践\Software_testing\vggt-main"
& "D:\anaconda3\envs\Pytorch_Vggt\python.exe" ".\demo_gradio_cn.py"
```

不要从其他工作目录直接调用该 Python 文件，否则脚本中现有的相对路径可能无法解析。

### 4.3 停止服务

回到启动服务的终端并按 `Ctrl+C`。确认 Python 进程退出后再清理本次运行产物。不要在模型仍写文件时强行删除输出目录。

## 5. 可视化基本操作

1. 等待终端显示模型加载完成和本地 Gradio 地址。
2. 在浏览器中打开该地址。
3. 可上传 `vggt_input/single_cartoon/images/` 中的单张图片进行快速人工确认，也可选择其他现有图片序列或视频。
4. 点击 `Reconstruct`，等待三维重建完成。
5. 确认页面显示三维模型、运行状态和深度图；可切换相机显示、置信度阈值和预测模式观察界面行为。
6. 确认运行产物位于本次 `input_images_...` 工作目录，并按现有逻辑备份至 `vggt_output/gradio/`。

本节仅用于确认外围改动没有破坏既有可视化功能，不计入模块一的 30 条正式测试用例。

## 6. 人工建立模块一测试工程

1. 小组先人工确定需求、测试范围和测试编号规则。
2. 围绕确定性几何模块人工设计不少于 30 条用例，并把每条用例录入附录1 Excel。
3. 至少采用等价类、边界值、场景法中的两种方法，在“备注”列逐条标明设计方法。
4. 在 `tests/` 中人工实现对应的 pytest 测试，至少 24 条实现自动化，建议全部自动化。
5. 人工创建根目录 `run_tests.ps1`，设置 `vggt-main` 的导入路径并统一运行全部测试。
6. 测试代码不得导入 `demo_gradio_cn.py`；该脚本导入时会加载模型并启动网页服务，不适合作为单元测试依赖。
7. 为每项测试建立“需求—用例—测试函数—执行结果—缺陷”的可追溯关系。

## 7. 运行人工编写的测试

人工完成 `run_tests.ps1` 后，在仓库根目录运行：

```powershell
powershell -ExecutionPolicy Bypass -File .\run_tests.ps1
```

一键入口至少应完成以下工作：

- 检查测试依赖；
- 运行全部人工编写的自动化用例；
- 在终端输出用例总数、通过数、失败数和跳过数；
- 把 JUnit XML 和完整日志保存至 `test_results/module1/`；
- 以非零退出码表示测试失败。

当前仓库没有由 AI 生成的 `run_tests.ps1` 或计分测试代码。运行前应确认这些文件已经由小组成员人工完成并提交。

## 8. 填写测试用例清单

1. 打开 `VGGT模块一测试用例清单_待人工填写.xlsx`。
2. 在“文档信息”页补全产品版本、项目编号、拟制人、评审人、批准人和日期。
3. 在“测试用例”页逐条填写测试编号、测试项、标题、重要级别、是否自动化、预置条件、输入、步骤、预期结果、实际结果、状态和测试方法。
4. 测试编号应使用小组统一规则，并能关联测试函数和缺陷编号。
5. 预期结果必须可判定；实际结果和状态只能在真实执行后填写。
6. 检查首页统计与测试日志一致。不得用手工修改汇总数字掩盖明细差异。

## 9. 缺陷记录与复测

1. 测试失败后先排除用例、环境和数据问题，再判断是否为软件缺陷。
2. 对有效缺陷记录测试环境、软件版本、关联用例、复现步骤、预期结果、实际结果、严重程度、优先级、附件和发现人。
3. 保存能够证明问题的终端日志、截图或最小输入，附件名称包含缺陷编号。
4. 修复时记录解决者、解决日期、修复提交、解决方案和影响范围。
5. 使用原失败用例复测，并执行相关回归测试。
6. 只有复测通过后才能关闭缺陷。模块一最终至少需要 3 个真实、有效且有修复验证的缺陷，不得虚构或拆分同一问题凑数。

## 10. 测试报告填写

按照附录3依次填写：被测对象概述、测试范围、测试策略、测试环境、用例总览、5–8 个典型用例、需求—用例分布、自动化架构、关键实现、执行结果、缺陷摘要、典型缺陷根因、质量结论和成员贡献度。

报告中的用例数、通过数、失败数、通过率和缺陷数必须与 Excel、JUnit XML、日志及缺陷报告一致。成员贡献度总和必须等于 100%，并能由个人 Git 提交记录支撑。

## 11. 证据截图与文件命名

- 截图应包含可识别的测试编号、时间、版本或终端命令。
- 建议使用“编号_简短说明_日期”的命名方式。
- 原始日志保留完整版本，报告中只引用必要片段。
- 不在截图、日志或报告中暴露密码、令牌、本地证书和其他敏感信息。
- 不把可再生的大型 GLB、点云、缓存和模型权重提交到仓库。

## 12. 常见问题

### 找不到模型权重

确认 `model.pt` 位于实践目录根部。外层启动脚本会在启动前检查该路径。

### 找不到 Python 或依赖

通过 `-PythonExecutable` 指定 `Pytorch_Vggt` 环境中的 `python.exe`，并在该环境中安装项目依赖。

### 相对路径或示例素材报错

使用 `run_vggt_demo.ps1`，或先进入 `vggt-main` 再直接运行 Python 文件。

### 端口被占用

检查是否仍有上一次启动的服务。当前程序会尝试处理默认端口冲突，仍失败时应先正常停止旧进程再重试。

### CUDA 不可用或显存不足

确认启动程序使用的是正确 Conda 环境和 GPU。关闭其他占用显存的任务，并先用单张图片进行功能确认。

### 测试统计不一致

以原始执行日志和 JUnit XML 为依据，逐条核对 Excel 的实际结果和状态；不要直接修改报告汇总数字。

## 13. 输出清理

1. 确认需要保留的日志、截图和缺陷证据已经归档。
2. 确认 Gradio 服务已停止。
3. 只清理确认可再生的 `input_images_...`、GLB、点云和临时缓存。
4. 保留 `vggt_output/README.md`、`.gitkeep` 和正式测试证据。
5. 清理后运行 Git 状态检查，确认没有误删源码或意外加入大文件。

## 14. PPT 与演示视频

模块一 PPT 建议控制在 10–12 页、讲解 5–8 分钟，突出被测模块、主要策略、关键数字、一个典型缺陷和一个有价值的测试难点，不直接复制测试报告全文。

演示视频应展示 VGGT 核心功能、人工编写的一键测试入口、真实执行结果和典型缺陷证据。录制前关闭含密码、账号或私人路径信息的窗口。

## 15. 提交前检查

提交前逐项核对 `交付检查清单.md`。特别确认：用例不少于 30 条、自动化不少于 24 条、至少两种设计方法、至少 3 个有效缺陷、统计一致、贡献度合计 100%、成员提交记录独立，并且 `vggt-main` 没有无关改动。
